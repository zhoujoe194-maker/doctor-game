# 产品与算法设计

## 当前确定的方向

- 无畏契约，Windows 桌面场景，后台观察，赛后给建议。
- 结合玩家自报的瞄准方式、握姿、操作空间和控制感。
- 优先分析击杀、被击杀、发生对枪但未造成击杀，以及预瞄过程。
- 输出可追溯的片段、可解释的假设和复测方案；不承诺看一局就能找到唯一最佳值。

## 四种场景如何分析

| 场景 | 应保留的上下文 | 优先观察 | 易混淆的因素 |
| --- | --- | --- | --- |
| 完成击杀 | 击杀前的接敌与对准过程，事件之后短暂余量 | 首次移动落点、是否越过后回拉、修正次数 | 击杀可能来自站位、敌人静止或运气；结果好不等于参数合适 |
| 被击杀 | 死亡前接敌、移动和射击过程 | 有没有开始反应、到达目标前是否过度修正 | 背身、被闪、多人夹击、枪械与血量差不能归因于灵敏度 |
| 对枪未击杀 | 首次有效目标出现到交战结束 | 是否反复从目标两侧扫过、持续跟踪误差、是否来不及补拉 | 敌人移动、掩体、压枪、投射物和撤退决策 |
| 预瞄 | 转角、换点、搜索视线的完整片段 | 视角轨迹、终点减速、非必要反转、粗调和微调的衔接 | 主动搜点本来就包含甩动和停顿，不能只追求轨迹平滑 |

自动事件定位应与精细瞄准分析分成两个阶段。定位阶段可以低频扫描击杀提示、己方死亡界面、比分和射击线索，再对事件前后的原始高帧率录像细读。窗口长度要由真实样本标注验证，不能把一个固定秒数当作每次对枪的完整边界。

**当前实现状态：**颜色轨迹候选、低频背景位移候选和本地 HUD 击杀信息 OCR 已实现。HUD 会根据本局玩家名给出本人击杀/死亡候选，附时间、左右参与者、置信度和来源；仍然只是观察候选，必须回放确认。未实现死亡界面分类、交战边界识别或真实准确率评估。

## 习惯信息如何影响分析

| 信息 | 当前作用 | 后续数据足够时可验证的假设 |
| --- | --- | --- |
| 手臂为主 | 复测远距离微调和大幅移动结束后的补拉 | 大幅位移和精细修正的误差分布是否不同 |
| 手腕为主 | 增加大角度转身、抬鼠和空间余量的检查 | 灵敏度下降后，微调收益是否抵消转身成本 |
| 混合 | 分别记录大幅转向与小幅修正的表现 | 两种动作交接处是否出现额外修正 |
| 趴握/抓握/指握 | 作为固定的实验条件和分组特征 | 握姿与个人变化趋势是否有关，而非先设固定映射 |
| 可移动宽度与控制感 | 标明空间限制与主观控制成本 | 改变参数后是否更常触边或更难放松控制 |

只看游戏录像无法知道玩家确实用了手臂、手腕还是手指。当前只能使用自报信息；将来如引入手部摄像头，应作为独立可选采集，不假设录像里已经存在这些信息。

## 平滑度的定义

画面中心的准星通常不动。需要估计视角在世界中的转动，而不是把屏幕准星坐标画成轨迹。

当前原型用背景小块的匹配位移作为近似，计算方向反转和低频速度。它没有标定视角角度、FOV 或鼠标原始输入，也无法分开角色平移和视角旋转。因此界面使用「视角运动观察」，不用虚构的 0–100 平滑度评分。

更可靠的下一步是：估计全局相机旋转及质量，分离动态目标、角色平移、后坐力和抖动；按动作距离、持续时间和目标大小归一化；比较同一玩家相同场景在不同设置下的速度曲线与终点修正。低采样率无法识别高频微抖；提高指标复杂度不能补回缺失的信息。

## 数据与有效性验证

1. 获取明确同意使用的真实玩家录像，保留真实帧率、分辨率、游戏版本和设置快照。
2. 标注击杀/死亡/交战边界、预瞄意图、目标框、初次移动起止、压枪、观战、特效遮挡和样本可用性。
3. 按玩家划分开发与测试数据，避免同一玩家相邻片段同时进入训练和测试。
4. 分别评估事件召回率、目标跟踪误差、误检片段比例、用户确认负担；不能用最终击杀率替代检测评估。
5. 使用玩家内随机交叉对比原值与候选值，固定设备/握姿/游戏参数，平衡顺序，留出适应时间，多次复测，记录客观任务表现与控制感。
6. 在确认改善前保持「试验候选」措辞。允许保持原值和撤销变化，避免每天因噪声来回调参。

## 下一阶段优先级

先收集真实录像、验证关键事件和目标跟踪，再验证相机运动分解。随后把手部习惯作为带置信度的上下文，验证是否改善个体推荐。HUD 事件需要额外的真实对局评估：按玩家、HUD 缩放、语言和分辨率分层，报告行级及事件级 precision/recall、时间边界误差、低置信度拒绝率和复核负担；合成录像测试只证明管线可用，不证明游戏内识别准确。上线前独立完成 Windows 游戏性能、捕获兼容性和平台产品审核；原型的合成测试不替代这些步骤。
